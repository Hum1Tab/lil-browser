# PX2: 広告遮断コストのプローブ結果

日付: 2026-10-23
環境: Windows 11 Home 10.0.26200、WebView2 Runtime 155.0.4283.62、.NET SDK 8.0.426
コード: [`prototype/px1-webview2/`](../px1-webview2/)（`--adblock` モード）
サーバー: [`prototype/px2-server/server.py`](../px2-server/server.py)
生データ: [`prototype/results/px2-none/`](../results/px2-none/)、[`px2-all-allow/`](../results/px2-all-allow/)、[`px2-all/`](../results/px2-all/)、[`px2-hybrid/`](../results/px2-hybrid/)

## 1. 目的

「全件の `WebResourceRequested` はホスト UI スレッドとの往復でページを遅くする」という設計上の前提を、A/B で測る。あわせて、遮断による短縮と、遮断の有無によるコストを分離する。

## 2. 方法

ローカル HTTP サーバーが 1 ページに **250 枚の広告画像（`/ad/`）と 250 枚のコンテンツ画像（`/content/`）** を配置する。各画像は 2ms の遅延を入れて返す。ページは `Cache-Control: no-store`。

WebView2 アプリに次のモードを実装した。

| モード | フィルタ | 遮断 | 意図 |
|---|---|---|---|
| `none` | なし | なし | ベースライン |
| `all-allow` | `*` | なし | 全件フックの純コスト |
| `all` | `*` | `/ad/` を 204 | 全件フック + 遮断 |
| `hybrid` | `http://127.0.0.1:8765/ad/*` | `/ad/` を 204 | 広告だけフック + 遮断 |

各モードを 5 回ずつ、別プロセス・別 UDF で実行した。計測は、`Navigate` から `NavigationCompleted` までの Stopwatch と、`performance.getEntriesByType('navigation')[0].duration`。リクエスト数はホストのカウンタで数えた。

## 3. 結果

| モード | ナビゲーション中央値 | フックしたリクエスト | 遮断 |
|---|---:|---:|---:|
| none | 324ms | 0 | 0 |
| all-allow | 321ms | 501 | 0 |
| all | 243ms | 501 | 250 |
| hybrid | 208ms | 250 | 250 |

5 回の値:

- none: 330, 321, 324, 319, 333
- all-allow: 348, 320, 321, 313, 334
- all: 269, 256, 230, 243, 243
- hybrid: 234, 208, 207, 214, 200

`performance` のリソース数は全モードで 250 で頭打ちになった。これは Resource Timing のバッファ上限（250）によるもので、実際のリクエスト数はホストのカウンタ（501 / 250）で確認した。

## 4. 解釈

1. **全件フックの純コストは、この規模では観測できなかった。** `none` 324ms に対し `all-allow` 321ms。501 リクエストをホストに通しても、ナビゲーション時間は変わらない。
2. **遮断はネットワーク時間を減らす。** `all` 243ms、`hybrid` 208ms。250 枚の画像を 204 で返すことで、2ms の遅延と転送がなくなる。
3. **`hybrid` が最も速い。** 広告だけをフックし、コンテンツはフックしない。往復を半分にし、遮断の効果は同じ。
4. **「UI スレッド往復が広告遮断のボトルネック」という一般化は、この環境では支持されない。** ただし、これはローカルページ、小さな画像、UI スレッドが idle の条件である。

## 5. 設計への影響

- F2（広告遮断の構造的天井）のうち、**性能の主張は弱める**。ボトルネックは、速度ではなく **カバレッジと精度** である。
- カバレッジの制約は残る:
  - 発信元フレーム URL が無いため、`$third-party` / `$domain` は近似。
  - WebSocket では `WebResourceRequested` が発火しない。
  - `$csp` はレスポンスヘッダを変更できない。
  - サービスワーカーの文脈が無い。
- `hybrid` を主方式にする設計は、性能の面でも妥当である。
- EasyList 全件の照合（adblock-rust）を加えたコストは、このテストに含まれていない。別途 PX2b で測る。

## 6. 限界

- ローカルサーバー、1 ページ、小さな画像、UI スレッド idle。
- 5 回の測定。分散は 20〜30ms 程度。
- adblock-rust のルール照合、cosmetic 注入、スクリプトレットを含まない。
- 実サイトの JavaScript、レイアウト、GPU、ネットワークを含まない。
- 遮断は `/ad/` のパス文字列だけ。フィルタの複雑さがない。
- Resource Timing のバッファ上限 250 のため、リソース数は参考値。

## 7. 次の試験

1. adblock-rust に EasyList のサブセット（1 万〜5 万ルール）を読み込ませ、同じ A/B を行う（PX2b）。
2. 実サイト 5 件で、遮断 ON/OFF の LCP / Load / CPU を測る。
3. 1000 リクエスト、UI スレッドに負荷をかけた状態で、往復コストを再測する。
4. cosmetic 注入の FOUC とレイアウトシフトを測る。
5. WebSocket を使うページで、遮断の抜けを確認する。
