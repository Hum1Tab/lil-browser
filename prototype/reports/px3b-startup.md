# PX3b: 公平な起動比較（初期）

日付: 2026-10-23
環境: Windows 11 Home 10.0.26200、WebView2 Runtime 155.0.4283.62
コード: [`prototype/px3-tabs/`](../px3-tabs/)（`--startup-only`）、計測: [`prototype/px3b-startup.ps1`](../px3b-startup.ps1)
サーバー: [`prototype/px3-server/server.py`](../px3-server/server.py)（load ビーコン）
生データ: [`prototype/results/px3b-*`](../results/)

## 1. 目的

PX3 の起動比較は、本が全タブ読込完了、Edge がウィンドウ表示で、定義が違っていた。PX3b では、**ページの `load` イベントからローカルサーバーへビーコンを送り、プロセス開始から最初のタブの load 完了まで**を、本と Edge で同じ定義で測る。

あわせて、本プロトタイプに `--startup-only` を追加した。N タブを設定しても、起動時は最初のタブだけを生成・読み込み、他は空のタブページとして残す。設計の「遅延復元」に近い。

## 2. 方法

- `px3-server` のページは `load` で `/mark?run=<id>&tab=<n>&t=<perf>` にビーコンを送る。サーバーは受信時刻を記録する。
- 計測スクリプトは、`Start-Process` の直前に UTC ミリ秒を記録し、`/marks?run=<id>` の `tab=1` の受信時刻との差を起動時間とする。
- 本: `--startup-only --run <id> --tabs N`。Edge: 同じ URL を N 個、`--new-window` で渡す。
- 各条件 3 回。1 回ごとに新しい UDF / Edge プロファイル。

## 3. 結果

### 3.1 起動時間（プロセス開始 → 最初のタブの load）

| タブ | 本（中央値） | 本（3 回） | Edge（中央値） | Edge（3 回） |
|---:|---:|---|---:|---|
| 1 | **5,135ms** | 6,294 / 5,135 / 4,101 | **5,896ms** | 5,896 / 5,547 / 7,784 |
| 5 | **4,238ms** | 4,031 / 4,238 / 4,610 | **7,563ms** | 7,563 / 6,398 / 8,573 |
| 20 | **7,470ms** | 5,028 / 7,470 / 9,928 | **6,730ms** | 9,727 / 6,687 / 6,730 |

### 3.2 ページ内の `performance` 値

ビーコンの `perf` は、ページ内の `load` 時点の `performance.now()` である。値は 3.4〜8.7 秒で、同じページでも大きくばらついた。サーバーはローカルで、10 枚の 1x1 画像しか返していない。したがって、このばらつきは、ページ内容ではなく、WebView2 / Edge の起動、プロファイル生成、Defender、システム負荷に由来する可能性が高い。

## 4. 解釈

1. **1 タブでは、本がわずかに速い（5.13s vs 5.90s）。** ただし差は 13% で、3 回の範囲は重なっている。優位とは言えない。
2. **5 タブでは、本が速い（4.24s vs 7.56s）。** 本は最初のタブだけを読む。Edge は 5 タブを読む。これは「遅延復元」の効果であり、5 タブ全部が読めるまでの時間ではない。
3. **20 タブでは、本が遅い（7.47s vs 6.73s）。** 本は 20 個の空タブページを作るコストがあり、システム負荷の影響も受けた。遅延復元の優位は、この条件では確認できない。
4. **絶対値が大きすぎる。** ローカルページで 4〜10 秒は、ページ内容では説明できない。測定環境（バックグラウンドのゲーム/配信、Defender、WebView2 の初回プロファイル）が影響している可能性が高い。
5. **結論**: 起動は「1 タブは同等、5 タブは遅延復元で有利、20 タブは未確定」。**「Edge より起動が速い」とは、まだ主張できない。**

## 5. 設計への影響

- F3 の起動部分は「未証明」のまま。1 タブの小さな優位と、5 タブの遅延復元の優位は、追加検証の価値がある。
- 20 タブの起動で負けたことは、設計の「起動時に全タブを復元しない」方針の重要性を示す。空タブページの生成コストも削る必要がある（タブモデルだけ先に作り、WebView は選択時に作る）。
- 起動の主張は、静かな環境で 10 回以上、実サイトで測るまで保留する。

## 6. 限界

- 各条件 3 回。分散が大きく、中央値の差がノイズに埋もれている。
- 測定環境が静かでない。バックグラウンドの負荷を統制していない。
- ページはローカル、10 画像。実サイトのネットワーク、JS、広告を含まない。
- Edge は 5/20 タブをすべて読む。本は最初のタブだけ。比較は「最初のタブが使えるまで」であり、「全タブが使えるまで」ではない。
- 20 タブの本は、空の TabPage を 20 個作る。WebView は 1 個だけ。
- ビーコンの受信時刻は、サーバーのスレッド処理とログ書き込みを含む。誤差は小さいが、ゼロではない。

## 7. 次の試験（PX3c）

1. 静かな環境（バックグラウンド停止、Defender のスキャン完了後）で、10 回以上。
2. 実サイト 20 件（異なるオリジン）で、最初のタブの load と、全タブの load を分けて測る。
3. 空タブページの生成コストを削る（タブモデルだけ先に作り、WebView は選択時に生成）。
4. タブ切替で未読込タブを選んだときの load 時間を測る。
5. `TrySuspendAsync` / 破棄のメモリと復帰時間を測る。
