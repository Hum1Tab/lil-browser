# PX3c: 暖機後の起動比較 — 「起動が速い」の反証

日付: 2026-10-23
環境: Windows 11 Home 10.0.26200、WebView2 Runtime 155.0.4283.62
コード: [`prototype/px3-tabs/`](../px3-tabs/)（`--startup-only --udf`）、計測: [`prototype/px3c-warm.ps1`](../px3c-warm.ps1)
サーバー: [`prototype/px3-server/server.py`](../px3-server/server.py)（load ビーコン）
生データ: [`prototype/results/px3c-*`](../results/)

## 1. 目的

PX3b の起動比較は、毎回新しい UDF / Edge プロファイルを作る「コールド」条件で、分散が大きかった。実際の日常利用に近い **暖機後（同じ UDF / プロファイルを再利用）** で、本と Edge の起動を同じ定義で測る。

## 2. 方法

- 本: `--startup-only --udf <固定パス>`。起動時は最初のタブだけを生成し、他は作らない。UDF は実行間で再利用。
- Edge: 同じ `--user-data-dir` を実行間で再利用。
- ページの `load` ビーコンで、プロセス開始から最初のタブの load 完了までを測る。
- 各条件 5 回。1 回目（コールド）を除いた 4 回の中央値（スクリプトは upper median）を「暖機後」とする。
- 1 回ごとにプロセスツリーを停止し、1 秒待ってから次を起動。

## 3. 結果

### 3.1 暖機後の起動（プロセス開始 → 最初のタブの load）

| タブ | 本（暖機後） | Edge（暖機後） | 差 |
|---:|---:|---:|---:|
| 1 | 481.5ms | **293.1ms** | 本が +64% 遅い |
| 5 | 456.3ms | **310.5ms** | 本が +47% 遅い |
| 20 | **533.8ms** | 588.8ms | 本が -9% 速い（本は最初のタブのみ） |

### 3.2 コールドと暖機の差

| 条件 | 本コールド | 本暖機 | Edge コールド | Edge 暖機 |
|---|---:|---:|---:|---:|
| 1 タブ | 4,835ms | 482ms | 5,808ms | 293ms |
| 5 タブ | 4,655ms | 456ms | 6,645ms | 311ms |
| 20 タブ | 4,991ms | 534ms | 6,275ms | 589ms |

コールドは、本も Edge も 4.6〜6.6 秒かかる。暖機すると、本は約 0.5 秒、Edge は約 0.3 秒になる。**Edge の暖機後の速さは、スタートアップブースト / 事前起動 / OS 統合によるもので、本プロトタイプには無い。**

### 3.3 5 回の値（暖機後の 4 回）

- 本 1 タブ: 477.6 / 481.5 / 496.3 / 467.0 → 481.5ms
- Edge 1 タブ: 293.1 / 289.6 / 283.7 / 321.1 → 293.1ms
- 本 5 タブ: 456.3 / 466.1 / 455.8 / 454.0 → 456.3ms
- Edge 5 タブ: 309.7 / 309.6 / 310.5 / 336.6 → 310.5ms
- 本 20 タブ: 503.5 / 543.7 / 533.8 / 483.8 → 533.8ms
- Edge 20 タブ: 599.4 / 588.8 / 566.2 / 566.5 → 588.8ms

## 4. 解釈

1. **1 タブと 5 タブでは、Edge の暖機後起動が本より明確に速い。** 本 481ms vs 293ms、456ms vs 310ms。差は 47〜64% で、分散（±20ms）より大きい。
2. **20 タブでは本がわずかに速いが、比較は不公平である。** 本は最初のタブしか読まない。Edge は 20 タブを読む。それでも Edge の最初のタブは 589ms で、本の 534ms と同程度である。
3. **「起動が Edge より速い」という設計の主張は、暖機後では成立しない。** コールドの比較は分散が大きく、優劣を決められなかった。暖機後は Edge が勝つ。
4. **起動の速さを製品の差別化にするなら、スタートアップブースト / 事前起動が必要である。** それは常駐プロセスとメモリを増やし、「軽い」というもう一つの差別化と衝突する。
5. **メモリの優位（PX3）は残る。** ただし「メモリが軽い」だけでは、乗り換えの理由として弱い。

## 5. 設計への影響

- Gate 1 の「5 タブメモリと起動の両方で Edge を上回る」は、**起動で不合格**。メモリは合格方向。
- 設計の製品定義「起動・待機・メモリのベースラインを既存ブラウザより小さく」のうち、**起動は撤回**する。
- 「軽量 + 高速」を看板にするなら、この設計は成立しない。残る看板は「メモリが軽い」「プライバシー」「制御性」だが、いずれも Edge に対する決定的な優位ではない。
- 起動の挽回には、事前起動（メモリ増）か、OS 統合（Windows のスタートアップ登録、タスクスケジューラ）が必要になる。前者はメモリの優位を削り、後者は常駐とプライバシーの問題を生む。

## 6. 限界

- ローカル、軽量ページ。実サイトのネットワークと JS を含まない。
- 本プロトタイプには UI、タブストリップ、セッション復元、スタートアップブーストが無い。
- Edge はスタートアップブーストと OS 統合を持つ。条件は公平だが、製品としては本側が同じ仕組みを持てないわけではない。
- 5 回、1 台、1 バージョン。OS 再起動後のコールドは未測定。
- 暖機後の Edge は、前回のプロセスが完全に終了していない可能性がある（1 秒待ち）。その場合、Edge に有利に働く。
- 20 タブの本は最初のタブのみ。Edge は 20 タブ。比較は「最初のタブが使えるまで」であり、「全タブが使えるまで」ではない。

## 7. 次の判断

1. 「起動が速い」を諦め、「メモリが軽い + プライバシー」に絞る。ただし差別化は弱い。
2. 事前起動を実装し、メモリとのトレードオフを測る。常駐 1 プロセスで起動 200ms を狙うなら、メモリ +50〜100MB を受け入れる必要がある。
3. 起動の速さを必須にするなら、WebView2 ではなく OS 統合された既存エンジン（Edge）を使う。つまり、この製品の意味がなくなる。
4. 設計の最終回答を「B' は推奨しない」に変更するか、看板を「軽量 + 高速」から「プライバシー + 制御」に変えて再定義する。
