# 02. 技術選定の評価

状態: 確定（推奨 B）。ただし重み次第で A が勝つことを明示する。
確信度: 高（エンジン能力は一次資料で確認）、中（開発コストと将来の保守性は推定）

## 1. 評価の前提

### 1.1 要求の優先順位

要求をそのまま並べると、互いに矛盾する。設計に先立ち、優先順位を明示する。

| 優先 | 要求 | 理由 |
|---|---|---|
| 1 | セキュリティ更新を継続できる | 更新できないブラウザは、機能が多くても安全ではない |
| 2 | Web 互換性（対象範囲内） | 日常利用できないブラウザは製品にならない |
| 3 | 軽量性・応答性 | 競争力の中心 |
| 4 | 攻撃面の小ささ | ホスト側の新規コードを最小化する |
| 5 | 広告遮断の自由度 | 差別化要素。ただしエンジン制約を受ける |
| 6 | 開発コスト | 現実性。ただし 1〜4 を犠牲にしてまで下げない |

### 3.3 プロセスモデルの要点

【事実】WebView2 は Edge と同じプロセスモデルを使う。1 つの user data folder に対して 1 つのブラウザプロセスがあり、レンダラはサイト分離に応じて共有・分割される [S05]。複数プロファイルは同一 UDF 内で分離でき、ブラウザプロセスを増やさない [S07]。

【推測】したがって、タブごとに 1 つの WebView2 コントローラを作っても、ブラウザプロセスは 1 つに収まる。メモリの支配要因はレンダラと GPU であり、ホストのタブ管理コードではない。この性質は「タブを増やしてもホストの固定費が増えない」ことを意味する。

### 3.4 ライフサイクル

| 対象 | 生成 | 破棄 | 注意 |
|---|---|---|---|
| `CoreWebView2Environment` | 起動時に 1 回 | プロセス終了時 | UDF ごとに 1 つ [S05] |
| `CoreWebView2Controller` | タブ生成時 | タブ閉鎖・Cold 化時 | `Close` で安全に終了 [S05] |
| プロファイル | 初回指定時に作成 | 明示削除 | 同一 UDF 内 [S07] |
| ブラウザプロセス | 最初の環境生成時 | 全コントローラの終了後 | `BrowserProcessId` で監視 |
| ランタイム更新 | `NewBrowserVersionAvailable` | 再起動で反映 | 実行中は旧版 [S15] |

`ProcessFailed` でブラウザプロセス、レンダラ、GPU の失敗を区別する [S05]。ブラウザプロセスの失敗は全タブに影響するため、Cold からの復旧として扱う。

## 4. Tauri v2 の評価

### 4.1 Tauri が提供するもの

- ウィンドウ、メニュー、トレイ、単一インスタンス、バンドラ、署名付きアップデータ [S01][S35]。
- Capability による権限モデル。リモート URL への IPC は、capability の `remote.urls` を明示しない限り拒否される [S01]。
- `WebviewBuilder::data_directory` と `incognito`。WebView2 の UDF と InPrivate を指定できる [S03]。
- 複数 WebView を 1 ウィンドウに置く API（`Window::add_child`）[S03]。

### 4.2 Tauri を製品基盤にしない理由

#### 理由1: 全 WebView に IPC ブリッジを注入する

Tauri のソースは、WebView 生成時に次のスクリプトを無条件で注入する [S02]。

```js
Object.defineProperty(window, 'isTauri', { value: true });
if (!window.__TAURI_INTERNALS__) {
  Object.defineProperty(window, '__TAURI_INTERNALS__', { value: { plugins: {} } });
}
```

これはリモート URL のページにも入る。capability を絞れば**コマンド実行は拒否できる**が、**ブリッジオブジェクト自体はページに存在する**。ブラウザにとってこれは 2 つの意味で不要である。

1. フィンガープリンティングの材料になる（`window.isTauri` の有無で本ブラウザを識別できる）。
2. 将来の Tauri 脆弱性が、コンテンツページから到達可能な面として残る。

「capability で守っているから安全」は、攻撃面がゼロという意味ではない。ブラウザは、コンテンツページに**何も注入しない**のが原則である。

#### 理由2: ブラウザに必要な API が抽象化の下に隠れる

Tauri の WebView 抽象は、ウィンドウと WebView の生成・イベント・IPC を提供する。しかしブラウザには次が必要で、いずれも Tauri の公開 API では足りない。

- `WebResourceRequested` のフィルタ登録と同期的な応答
- プロファイル名を指定したコントローラ生成
- ダウンロードの詳細制御（パス、MIME、中断）
- 権限要求のオリジン別判断
- `TrySuspendAsync` と `MemoryUsageTargetLevel` の組み合わせ
- 新規ウィンドウ要求のポリシー判断

Tauri の `with_webview` で生の `ICoreWebView2Controller` を取れるが、そこから先は結局 COM を直接叩く。ならば最初から直接叩く方が、抽象の二重化を避けられる。

#### 理由3: 複数 WebView API が `unstable` 機能である

`Window::add_child` は `unstable` feature の下にある [S03]。ブラウザのタブ配置は中核機能であり、unstable な API に依存するのは保守上不利である。

#### 理由4: サイズの利点がブラウザでは効かない

Tauri の売りは小さいバイナリ [S04]。しかしブラウザでは、エンジン（WebView2 Runtime）が既にシステムにあり、ホストのバイナリサイズは支配要因ではない。数百 KB の差より、API 制御の自由度と攻撃面の方が重要である。

### 4.3 Tauri を使ってよい場面

- Phase 0 の計測プロトタイプ。タブ 5 枚、アドレスバー、WebResourceRequested の簡易フックを 1〜2 週間で作り、起動・メモリ・遮断コストを測る。
- 3 か月以内に MVP を出す必要があり、UI の実装コストを優先する場合。capability を絞り、リモート IPC を許可しないことを条件とする。
- 社内ツール。コンテンツが信頼できる場合。
- ブラウザ以外のデスクトップアプリ。

ただし、製品の第一候補は wry である。Tauri の許容は「MVP の妥協」であり、長期の製品基盤ではない。9.4 を参照。

## 5. CEF の評価

### 5.1 利点

- Chromium をフルに制御できる。通信フックは `CefRequestHandler` で行え、WebView2 のような「ホスト UI スレッドへの往復」を強制しない。
- サンドボックスとマルチプロセスを持つ。
- 広告遮断の自由度は高い（リクエストの文脈、レスポンスの書換、CSP 付与）。

### 5.2 欠点

- 配布物が大きい。Chromium ランタイムを同梱するため、WebView2 の Fixed Version が 250MB 超であることから類推しても、CEF の配布物は数百 MB 規模になる [S15]（類推であり、CEF 配布物の実測ではない）。
- セキュリティ更新を自分で追随する必要がある。Chromium は 2 週間ごとにマイルストーンを出し、毎週セキュリティ更新を出す [S29]。CEF のビルドを待つにせよ、自前でビルドするにせよ、追随責任は開発側にある。
- ブラウザ拡張は CEF でも提供されない（Chrome 拡張 API の実装ではない）。したがって uBO は使えない。
- Widevine はライセンスが必要で、同梱できる保証がない。CEF にすれば DRM が解決するわけではない。
- Google OAuth は、CEF を「埋め込み WebView」と判定されれば拒否される。判定は UA とポリシー次第で、安定した保証はない。

【評価】CEF は「互換性の壁」のうち拡張機能と DRM を解決しない。解決するのは Chromium フォークだけである。

## 6. Chromium フォークの評価

### 6.1 利点

- 拡張機能、Google ログイン、Widevine、Web Push、Payment API を、Chrome と同等に提供できる可能性がある。
- プロセスモデル、サンドボックス、サイト分離を自前で制御できる。

### 6.2 欠点

- セキュリティ更新の追随が必須。Chromium は 2 週間ごとにマイルストーン、毎週のセキュリティ更新である [S29]。追随が 1 週間遅れただけで、ゼロデイ窓が開く。
- ビルド基盤、テスト、クラッシュ対応、GPU ドライバ問題、印刷、IME、アクセシビリティを自前で持つ。
- Widevine のライセンス契約が必要。
- 人月が桁違いになる。Brave 規模の組織でも継続的な投資が必要である。

【評価】「セキュリティ更新を継続できる」という最優先要求に対して、小規模チームの fork は**不利**である。更新を追随できない fork は、機能が多くても安全ではない。したがって、セキュリティを重視するほど fork は選びにくい。

## 7. Electron / ラッパーの評価

- Electron は Chromium を同梱するため、配布サイズとメモリの固定費が大きい。ブラウザの土台としては不利。
- 既存ブラウザのラッパー（`msedge.exe` を起動するだけ）は、軽量でもブラウザでもない。UI、タブ、遮断、保存のすべてを制御できない。製品要求を満たさない。

### 8.1 感度分析

重みは判断である。開発コストの重みを 5 から 25 に上げ、長期保守性を 10 から 5 に下げると、A は 5 点程度上がり、B は 4 点程度下がる。**短期の試作では A が勝ち、3 年保守する製品では B が勝つ。** この差は設計の優劣ではなく、時間軸の違いである。

なお、B の実装基盤は 9.4 で wry に変更した。スコアは概算のままとし、再評価は PX6（UI 工数）の後に行う。

したがって推奨は「B を製品に、A を Phase 0 の試作に」である。A を製品にしない理由は、スコア差ではなく、IPC ブリッジの注入と unstable API 依存という**構造的な問題**である。

## 9. 推奨

### 9.1 製品: B'（Rust + Win32 ネイティブ UI + wry 経由の WebView2）

- エンジン: WebView2 Runtime（Evergreen）。
- 言語: Rust（`unsafe` を原則禁止、COM 境界のみ限定）。
- UI: Win32 + Direct2D/DirectWrite。アドレスバーはネイティブ EDIT で IME を確保。
- WebView2 バインディング: wry + `webview2-com` + `windows` crate。wry は `controller()` と `environment()` を公開する [S44]。
- 広告遮断: adblock-rust（MPL-2.0）+ WebResourceRequested。ただし、主遮断はエンジンの追跡防止に置く（06 の 1.1）。
- 保存: SQLite（履歴）、WebView2 の UDF（Cookie/サイトデータ）。

Gate 0（9.5）を通る場合に限る。Gate 0 を通らないなら、CEF Chrome スタイル（PX7）を検討する。

### 9.2 試作: A（Tauri v2）

Phase 0 の 2〜3 週間だけ使う。目的は次の 3 つを測ること。

1. WebResourceRequested を全リクエストに適用したときのページ読み込み悪化。
2. 5 タブ / 20 タブの総メモリ。
3. コールドスタートとタブ切替。

試作コードは製品に持ち込まない。計測結果だけを持ち込む。

### 9.3 棄却

- C（CEF）: 拡張・DRM・認証の壁を解決せず、更新責任だけ増える。ただし、RequestContext レベルの拡張機能は動くため [S42]、「拡張が全く使えない」わけではない。Chrome スタイルの CEF は再検証の余地がある。
- D（Chromium fork）: セキュリティ更新の継続性が最優先要求に反する。資金と専任チームがある場合のみ再検討。
- E（Electron）: 固定費が大きい。
- F（ラッパー）: ブラウザではない。

### 9.4 反証レビューによる修正（2026-10-23）

[13-refutation-review.md](13-refutation-review.md) の結果、次の 3 点を修正する。

1. **第一候補を wry + ネイティブ UI に変更する。** wry は Tauri の下層で、Windows では `controller()` と `environment()` を公開する [S44]。Tauri のような `__TAURI_INTERNALS__` の自動注入が無く、タブを子 WebView として作れる。raw `webview2-com` は最大制御が必要な場合の第三候補にする。
2. **CEF の拡張機能を「不可」と断定しない。** CEF は Alloy スタイルで `chrome://extensions` をブロックするが、RequestContext レベルの拡張機能は動く [S42]。Chrome スタイルの CEF は、uBO と Google ログインを検証する価値がある。
3. **エンジン選定を Gate 0 に従属させる。** Chrome 拡張が必須なら、WebView2 は失格である。Widevine は PX4 で EME が supported だったが、実再生を確認する。Google ログインと Windows Hello パスキーは、PX1 で完全ログインと認証完了を確認する。Tauri か wry かは、この判定の後に決める。

Tauri の位置づけも修正する。Tauri は「製品に使わない」から「3 か月 MVP の妥協案」に変える。理由は、Tauri の問題（IPC 注入、unstable な複数 WebView）が、エンジンの問題（識別子、遮断、差別化）より小さいからである。

### 9.5 Gate 0（エンジン選定の前提）

| 要件 | 必須なら | WebView2 の判定 |
|---|---|---|
| Google ログイン | PX1 で完全ログインを確認。不可なら失格 | 識別子画面は表示 [S47]。完全ログインは未検証 |
| Windows Hello パスキー | PX1 で登録・認証の完了を確認。不可なら失格 | UVPAA=true、プロンプト起動 [S47]。完了は未検証 |
| Widevine | PX4 で実再生を確認。EME は supported | EME は supported [S48]。実再生は未検証 |
| Chrome 拡張 | CEF Chrome スタイル / Chromium フォーク | 失格 |

この表で 1 つでも「必須」なら、WebView2 を選ぶ理由は無い。Gate 0 を通った場合だけ、B（wry + ネイティブ UI）に進む。

## 11. 未解決

- WebView2 の Evergreen が、将来も Google OAuth のブロック対象であり続けるか。ポリシーは変わり得る。
- CEF の配布物サイズと、Widevine 同梱の可否。実測と法務確認が必要。
- Tauri の `unstable` が安定化するか。安定化しても、IPC 注入の問題は残る。
- WebView2 の `PreferredTrackingPreventionLevel` の実効性（どの程度の第三者 Cookie を止めるか）は、実測が必要 [S13]。
