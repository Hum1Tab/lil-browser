# 赤チームレビュー（設計の自己批判）

日付: 2026-10-23
対象: `01`〜`12` の設計文書
方法: 6 つの役割（実証主義者、論理学者、反対者、価値分析者、実務家、読者）で攻撃し、重大度を付けた。重大度は Critical / Major / Minor。

## 1. 総評

設計は「WebView2 で軽量ブラウザを作る」という当初の構想に対して、**成立条件を狭める結論**に到達した。これは後退ではなく、一次資料に基づく制約の反映である。ただし、次の 4 点は設計の根幹に関わるため、実装前に決着が必要である。

1. Google 認証を失うことが、対象ユーザーにとって致命的か。
2. 5 タブメモリで Edge を下回れるか。
3. WebResourceRequested のコストが、広告遮断を性能のボトルネックにしないか。
4. ネイティブ UI の工数が、1〜3 人で現実的か。

## 4. 8 つの問いへの回答

1. **Tauri v2 を本当に使うべきか** — 製品では使わない。試作だけ。根拠は IPC 注入 [S02] と unstable な複数 WebView [S03]。
2. **Brave や Edge より軽くできる合理的根拠があるか** — ベースライン（起動、アイドル、1〜5 タブ）には根拠がある。20〜50 タブでは、Edge の sleeping tabs [S27] に対して優位を主張できない。
3. **セキュリティ上の致命的な問題が残っていないか** — 残っている。ホストが設計上 MITM であること、フィルタ供給網、エンジン 0-day、同一ユーザーのマルウェアによる Cookie 窃取。いずれも「緩和はできるが、保証はできない」。
4. **Web 互換性で日常利用が困難にならないか** — Google ログインと DRM を必要とするユーザーには困難。対象を絞れば成立する。
5. **広告遮断が性能のボトルネックにならないか** — 全件フックならなる可能性が高い [S10]。ハイブリッドで抑えるが、実測が必要。
6. **Cookie と履歴だけの永続保存は現実的か** — 現実的でない。サイトデータを保存しないと壊れる [S06]。
7. **開発期間に対して複雑すぎないか** — 1 人では複雑。3 人でも 4〜6 か月。M0 で見積もりを再確認する。
8. **より小さく、より速く、より安全な設計は存在しないか** — 「既存ブラウザを設定して使うランチャー」は、より小さく安全だが、ブラウザではない。kiosk 特化の WebView2 アプリは、より小さく安全だが、汎用ブラウザではない。汎用ブラウザとしての要求を満たす範囲では、B が妥当である。

## 5. 結論

Critical は 1 件（Google 認証の欠落が当初目的を満たさない）。これは設計の欠陥ではなく、プラットフォームの制約である。製品定義を変えることで解消する。Major は複数あるが、いずれも測定・設計・運用で扱える。

このレビューを受けて、12 の最終推奨は「B を条件付きで採用し、Phase 0 で Go/No-Go を判定する」に修正された。
